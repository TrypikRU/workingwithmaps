# Движок синхронизации

Локальная БД — источник состояния интерфейса. SyncEngine отправляет только
сохранённую sync_queue. Бизнес-операция и вставка очереди выполняются одной
транзакцией репозитория.

## Компоненты

- SyncEngine.run() — последовательный проход по операциям, срок которых наступил.
  Возвращает SyncResult со счётчиками. Не зависит от Flutter, Riverpod и интерфейса.
- SyncProcessor — захват в SQLite, сериализация запроса, Dio, подтверждения и ошибки.
- SyncException — категории network, timeout, server, client, conflict, unsupported,
  invalidResponse, local и dependency.
- RetryPolicy — задержки 5, 10, 20, 40… секунд, максимум 15 минут, без лимита попыток.
- SyncLifecycle — связь с main: запуск при старте, возврате и каждые 15 секунд
  в открытом приложении. При сворачивании таймер выключается; начатый проход
  может завершиться.
- sync_providers.dart — зависимости и сводка SQLite для ручного запуска
  с сохранением ограничений nextRetryAt.

## Экран диагностики

Вкладка «Синхронизация» читает единый снимок SQLite через SyncDiagnosticsRepository
и Riverpod StreamProvider: последнее подтверждение, счётчики и текущие операции.
Для каждой записи показаны тип, идентификатор, действие, время создания,
число попыток, последняя ошибка, время повтора и статус.
Ошибочная операция открывает подробности с идентификатором операции.
Подписи, известные статусы и сообщения переведены на русский; хранимые ключи
протокола и сами данные не меняются. Старые текстовые ошибки тоже доступны.

«Синхронизировано» — накопительное количество подтверждённых операций с момента
включения диагностики, не число серверных сущностей. «Ожидает отправки»,
«Отправляется» и «Ошибки» относятся к текущей очереди. Ранние успехи задним числом
не восстанавливаются. Время успеха — последнее подтверждение, в том числе в
частично успешном проходе. Пустой запуск и ошибка не обновляют его.

sync.acknowledged_count и sync.last_success_at хранятся в app_metadata в той же
транзакции, что удаление очереди и подтверждение сущности. Отдельная миграция
не нужна; значения переживают перезапуск.

«Синхронизировать сейчас» учитывает сроки операций.
«Повторить ошибочные» вызывает run(retryFailed: true): под общей блокировкой
переводит failed в pending и снимает nextRetryAt, сохраняя attemptCount,
lastError, operationId и данные запроса. Повторяются 4xx и неподдерживаемые
операции, кроме 409: конфликт требует явного решения.
Если проход уже активен, ручной повтор ждёт его завершения.
Записи удаляются только после успешного подтверждения, а не по кнопке,
сроку хранения или при просмотре.

Индикатор подписан на общий поток движка в процессе и учитывает автоматические
и пустые проходы. Во время работы обе кнопки заблокированы.
Экран не импортирует Drift/Dio и сам не отправляет HTTP. После прокрутки
появляется кнопка «Наверх» для возврата к счётчикам и действиям.

## Состояния и порядок

Успех: pending → syncing → synced; строка очереди удаляется.
Ошибка: очередь и сущность получают failed, attemptCount увеличивается,
lastError содержит безопасный JSON с kind, message, statusCode и retryable.

Сетевые ошибки, превышение времени и 5xx получают nextRetryAt.
409 относится к conflict, остальные 4xx, включая 429 на этом этапе, — к client.
Автоматически они не повторяются. Неподдерживаемые операции, ошибки данных
и неверные подтверждения сохраняются для разбора.
Пользователь явно выбирает стратегию конфликта; посещение нельзя автоматически
перезаписать локальной версией. Движок не выбирает победителя сам.
[Подробности конфликтов](CONFLICTS.md).

Порядок задаёт локальный автоматически увеличивающийся идентификатор.
Операция не обгоняет повтор или конфликт своей сущности; другие сущности
продолжают работу. Проход ограничен максимальным идентификатором на старте:
новые записи не делают его бесконечным и обрабатываются следующим запуском.
Каждая операция выполняется максимум один раз за проход.

Внутри изолята запуски объединяются в один; между интерфейсом и WorkManager
действует блокировка SQLite. До восстановления движок атомарно получает
владение, которое проверяет каждая изменяющая транзакция.
[Фоновая синхронизация Android](BACKGROUND_SYNC.md).

## Транзакции и восстановление

Схема v3 добавляет sync_queue.operationId, payload и syncStatus.
Миграция сохраняет очередь v2, ссылки и поля повторов; новые записи имеют pending.
Перед первым HTTP-запросом обработчик одной транзакцией читает сущность,
фиксирует неизменяемый JSON запроса, случайный 128-битный operationId и syncing.
До первой отправки используется актуальное состояние сущности: это синхронизация
состояний, а не журнал каждой промежуточной правки.
После первого захвата содержимое запроса при повторах не меняется.

HTTP выполняется вне транзакции SQLite. Подтверждение проверяется по entityId
и serverVersion посещения. Удаление очереди и изменение syncStatus/serverVersion
фиксируются вместе. При наличии более новой операции статус остаётся pending;
старые поля не копируются поверх свежей локальной правки.
Следующая операция получает последнюю подтверждённую serverVersion.

После остановки процесса сохранённый syncing восстанавливается в pending
с теми же payload и operationId. Сетевые failed сохраняют задержки после перезапуска.
Если SQLite недоступна даже для записи ошибки, проход прерывается.
Следующий запуск восстанавливает незавершённый захват; частичной потери очереди нет.

## Идемпотентность и API

Поддерживаются:

- visit/upsert → POST /visits;
- location_point/upsert → POST /location/batch, по одной точке;
- route/create → POST /routes;
- object/patch, а также прежние upsert/update → PATCH /objects/{id}.

Идентификаторы назначаются клиентом и передаются неизменно.
Сервер исключает дубликаты посещений и точек по идентификатору и данным.
Идентичный повтор возвращает прежнюю версию; другие данные дают 409 даже
с актуальной serverVersion. Посещения и точки неизменяемы.

operationId передаётся как Idempotency-Key и используется в журнале.
Для PATCH сервер хранит OperationReceipts: ключ, точный запрос, исходный ответ.
Сущность и подтверждение фиксируются атомарно. Повтор не отменяет более поздние
серверные изменения. Это доставка не менее одного раза с идемпотентным применением,
а не обещание единственного сетевого запроса. Потеря ответа после фиксации
приводит к безопасному повтору без второго посещения и нового увеличения версии.

До подтверждения регистрации обхода связанные точки и посещения остаются
в очереди с повторяемой ошибкой dependency. Запрос с неизвестным routeId
не отправляется. Регистрация содержит неизменяемые id/name/date.
Завершение обхода пока сохраняется только локально.

API не поддерживает изменение обходов и удаление. Такие операции остаются failed
с категорией unsupported; данные не удаляются и не считаются подтверждёнными.
До отправки связанных данных сервер должен содержать objectId/routeId.
GET /sync и автоматическая загрузка обходов пока не подключены.
ObjectsRepository загружает объекты отдельно по ручному запросу.

## Диагностика и проверки

AppLogger пишет структурированные события в dart:developer с именем
«Полевой инспектор»: начало, присоединение, итог прохода, захват, успех, ошибка,
восстановление, attemptCount, elapsedMs и nextRetryAt. Журнал доступен в DevTools.
Координаты, данные запросов, HTTP-заголовки и исходный DioException не выводятся.
Получатель записей заменяем; его исключение не ломает синхронизацию.

~~~powershell
flutter analyze
flutter test
# Сервер должен работать с отдельной тестовой SQLite:
flutter test test/integration/sync_backend_test.dart --dart-define=SYNC_TEST_URL=http://127.0.0.1:5081/
~~~

Модульные и интеграционные тесты используют настоящие Drift/SQLite и подмену
транспорта Dio. Проверяются успех, отсутствие сети, 500/409/400, превышение времени,
частичный успех, задержки, перезапуск файловой БД, прерванный захват, дубликаты,
потеря подтверждения и параллельные движки.
Отдельный явно включаемый тест обращается к серверу, теряет ответ после фиксации
и проверяет единственное посещение с serverVersion=1 после повторов.
