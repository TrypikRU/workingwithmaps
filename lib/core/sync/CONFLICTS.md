# Конфликты и повторные локальные изменения

## Контракт версий

Objects и Visits хранят последнюю подтверждённую `serverVersion`, а не число
локальных нажатий «Сохранить». NULL означает неизвестную серверную версию.
GET /objects сохраняет версии в Drift, не публикует remote состояние напрямую в UI.

Для редактируемого объекта отправляется PATCH /objects/{id}. Например, запрос
с serverVersion=4 при серверной версии 5 получает HTTP 409 и полный snapshot
`current`. SyncProcessor атомарно сохраняет failed/lastError/attemptCount и запись
в `sync_conflicts`. `nextRetryAt=null`: обычный run, WorkManager и кнопка
«Повторить ошибочные» не повторяют 409. Эта операция блокирует последующие операции
той же сущности, но независимые сущности продолжают синхронизацию.

## Явные стратегии

В диагностике появился раздел «Конфликты и история решений». Диалог показывает
последние локальные поля и их serverVersion, серверные поля и версию, а также
фактически отправленный запрос. Это разные снимки, если пользователь изменил
сущность уже во время HTTP.

Для объекта доступны два решения:

- **Принять серверную**: принять показанные серверные бизнес-поля и версию, отменить
  конфликтную операцию и неотправленный хвост. Локальный вариант остаётся в истории.
  Локальная geometry сохраняется; pending completed Visits защищают статус visited.
- **Повторить локальную**: оставить последние локальные поля, принять показанную
  серверную версию как базу, заменить конфликт и неотправленный хвост одной новой
  PATCH-операцией. Её idempotency key будет новым. Если сервер уже изменился ещё
  раз, возникнет новый конфликт. Force-write и автоматического last-write-wins нет.

Visits — факты событий. Backend возвращает существующий Visit на идентичный повтор,
а любые другие поля с тем же ID дают 409, даже при совпадении версии. Кнопки
«Повторить локальную» для Visit нет; repository также запрещает такую стратегию.
Можно принять серверную запись, сохранив локальный факт в истории конфликта, либо
закрыть диалог и оставить конфликт нерешённым. Автоматического создания «исправляющего»
Visit под новым ID нет: оно могло бы превратить один факт в два события.

Если сервер не прислал корректный current (например debug=409), решение отключено.
«Обновить серверную версию» вызывает отдельный remote data source через repository,
сохраняет проверенный snapshot в SQLite и закрывает диалог. Откройте конфликт снова,
просмотрите свежие данные и выберите решение. Сетевая ошибка оставляет конфликт
нетронутым. Несуществующая на сервере запись остаётся для диагностики; автоматическое
создание/удаление не выполняется. Route/point 409 также сохраняются, но стратегии
для них пока не предусмотрены.

## A → B и coalescing

`saveObject` обновляет поля и очередь в одной транзакции. При повторных правках:

1. A ещё не отправлена (pending, attemptCount=0, payload/operationId=NULL): B
   объединяется с A. Сохраняется старший queue ID; при claim берётся актуальный
   объект из SQLite. В сеть уходит только последнее состояние.
2. A уже claimed, завершилась timeout или имеет frozen payload: A неизменна,
   потому что сервер мог её принять. B получает отдельную pending запись; C
   объединяется с ещё не отправленной B.
3. ACK A обновляет только serverVersion, не копирует старые бизнес-поля поверх B.
   B при своём claim получает подтверждённую версию A и текущие локальные поля.
4. При потерянном ACK A повторяется с прежними payload/key; сервер возвращает
   сохранённый receipt. Если другой клиент уже изменил сервер, B конфликтует с
   новой версией, вместо скрытой перезаписи чужих данных.

Coalescing используется только для object patch/update/legacy upsert, не для
Visits, точек GPS и регистрации маршрута. Размер прохода ограничен watermark:
новая B, созданная во время отправки A, может дождаться следующего запуска engine.
Старые уже отправленные payload никогда не переписываются «для оптимизации».

## Транзакции, восстановление и гонки

Drift v6 добавляет objects.serverVersion и отдельную sync_conflicts. История не имеет
каскадного FK на queue: удаление разрешённой операции не удаляет аудит. Сохраняются
queueId, entityType/id, requestPayload, localPayload, serverPayload, время и стратегия
решения. Решение не увеличивает счётчик ACK: он означает реальное подтверждение HTTP.

Разрешение получает тот же SQLite SyncLease, что UI/WorkManager SyncEngine. Изменение
сущности, отмена очереди, запись результата и enqueue новой PATCH выполняются в одной
транзакции. Если другой worker активен, действие предлагается повторить позднее.
Снимок из диалога сравнивается с текущей записью внутри транзакции: новая локальная
правка или обновлённая серверная версия требуют повторного просмотра. Двойное
нажатие/старый диалог не может повторно разрешить архивный конфликт. Ошибка SQLite
откатывает всё решение. Очередь, frozen payload и история переживают перезапуск.

Backend хранит OperationReceipts в собственной SQLite. Entity PATCH и receipt
коммитятся одним SaveChanges. Стабильный key + неизменный request возвращают исходный
response даже после последующих правок; тот же key с другим request даёт 409.
Это at-least-once доставка с идемпотентным применением. Ограничение pet-проекта:
receipts и аудит пока без TTL, UI истории не предназначен для миллионов конфликтов.

Логирование через AppLogger: sync.queue.coalesced, sync.conflict.detected,
sync.conflict.resolved и существующие claim/ACK/retry события. Payload координат
и полные записи в журнал не выводятся.

## Проверки

```powershell
flutter test test/core/sync/sync_conflict_test.dart
flutter test test/features/sync/sync_conflict_dialog_test.dart
flutter test test/drift
# На отдельном запущенном backend:
flutter test test/integration --dart-define=SYNC_TEST_URL=http://127.0.0.1:5096/
./backend/scripts/Smoke-Test.ps1 -BaseUrl http://127.0.0.1:5096
```

Unit tests проверяют 4→5/409, обе стратегии объектов, запрет перезаписи Visit,
несколько правок до claim и во время HTTP, потерю ACK, повторный конфликт, независимые
операции, stale review, lease, rollback, восстановление файловой БД и получение
snapshot после debug-ошибки. Widget tests проверяют сравнение версий и действия
через Riverpod/Drift. Сквозной тест использует настоящий API: GET→Drift, конфликт,
явный rebase, потерянный ACK, A/B/C и replay после более нового PATCH.
