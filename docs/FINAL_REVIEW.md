# Field Inspector — финальный аудит для портфолио

Дата: 14 сентября 2026. Проверены исходники Flutter/domain/data, SyncEngine,
платформенная граница Kotlin, тесты, API-контракты и документация. Работающая
архитектура и бизнес-логика в этом проходе не изменялись.

## Оценка для собеседования

По представленным инженерным задачам это **сильный Middle pet-проект с отдельными
решениями уровня Middle+**. Его ценность — в обработке отказов и владении данными,
а не в количестве подключённых пакетов. Уровень автора по репозиторию установить
нельзя: на интервью важно самостоятельно объяснить инварианты, показать код и
разобрать новые сценарии отказа.

| Тема для интервью | Что показать в коде / тестах | Какой вопрос стоит уметь разобрать |
| --- | --- | --- |
| 1. SQLite как источник состояния | ObjectsRepository, Drift streams, ObjectsRefreshController | Почему ошибка HTTP не переводит весь экран в error? |
| 2. Transactional outbox | VisitsRepository и Check-in rollback tests | Что произойдёт, если visit записался, а INSERT очереди упал? |
| 3. Идемпотентная доставка | Durable claim, frozen payload, backend OperationReceipts | Сервер закоммитил PATCH, ответ потерян: почему retry безопасен? |
| 4. Конкурентная синхронизация | Single-flight, SyncLease, тест второго isolate и late ACK | Почему mutex в Dart не защищает от WorkManager? |
| 5. Конфликты версий | SyncConflictRepository, диалог, immutable Visits | Почему не стоит автоматически выбирать last-write-wins для факта визита? |
| 6. Изменение во время HTTP | Queue coalescing, A/B/C, watermark, ACK version | Как подтвердить A и не затереть более новую локальную B? |
| 7. Нативная запись без UI | Kotlin service, TrackingStore, NativeTrackImporter | Что если Drift commit прошёл, а native ACK не дошёл? |
| 8. Проверяемая геометрия | Haversine, Ray Casting, CircularGeofence, GPS filter | Что считать границей polygon и почему reported speed недостаточно? |
| 9. Производительность карты и отдельные тайлы | Кэш слоёв, clustering O(n), тест на 500 объектов, offline package | Какие слои должны обновиться при GPS fix, а какие — только при изменении объектов? |

Дополнительный аргумент — воспроизводимые проверки: реальные SQLite-транзакции,
миграции, file reopen, виджеты с локальным cache, потерянные ACK и тестовый backend
с управляемыми отказами. Объясняйте, где тестируется алгоритм, где контракт, а где
требуется реальное Android-устройство.

## Приоритеты перед демонстрацией

1. **Записать реальные screenshots и короткий сценарий на устройстве.** Показать
   offline Check-in, закрытие/открытие приложения, возвращение сети, pending → synced,
   маршрут с погашенным экраном. Отдельно показать force-stop и восстановление:
   это не тот же сценарий, что сворачивание приложения.
2. **Измерить, а не предполагать производительность.** Тест 500 объектов проверяет
   корректность/повторное использование слоёв. FPS, память, нагрев и батарея требуют
   profile mode и физического устройства на продолжительном маршруте.
3. **Объяснить границы синхронизации.** GET /sync существует только в backend,
   завершение обхода не отправляется, UI-редактора объекта нет, geometry локальная.
   Native inbox переносится при доступном Flutter; worker отправляет только Drift queue.
4. **Следующий производственный шаг — эксплуатация.** Для выхода за рамки стенда
   потребуются authentication/HTTPS, полноценные backend migrations, политика хранения
   receipts/конфликтов, pagination и измерение длительных offline-очередей.
5. **Показать зелёный запуск CI после push.** Локальные проверки не подтверждают
   запуск на GitHub runner. Kotlin и Python тесты сейчас доступны локально, но
   отдельными шагами в CI не запускаются.
6. **Запланировать обновление Android toolchain.** Kotlin-тесты прошли, но Gradle
   сообщает о deprecated `android.builtInKotlin=false` / `android.newDsl=false`,
   KGP в workmanager_android и несовпадении embedded Kotlin Flutter build tooling.
   Это технический долг совместимости перед обновлением AGP/Gradle; в документационном
   аудите версии и работающая конфигурация намеренно не менялись.

В этом проходе не проверялись реальные датчики, battery/OEM ограничения, длительная
работа сервиса и загрузка настоящего лицензированного картографического пакета.
Проверка не является доказательством отсутствия всех возможных гонок. Нет оснований
переписывать существующие слои только ради формальной Clean Architecture; полезнее
закрыть перечисленные измеримые пробелы.
